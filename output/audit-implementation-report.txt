1. FINAL CODE AUDIT

Confirmed and fixed:
- Missing/null payment terms now normalize to immediate before validation. The central service also requires full payment for immediate stays. Explicit credit permits a partial payment.
- Check-in and stay extensions use a shared half-open reservation overlap rule. Adjacent checkout/arrival boundaries are accepted; overlapping extensions are rejected atomically.
- Reservation states now include booked, checked_in, completed, cancelled and no_show. Checkout completes the linked booking. Duplicate check-in/checkout and invalid transitions are rejected. Expiration includes the exact departure-time boundary. Booked dates can be edited with conflict checks.
- Later stay extension or checkout no longer rewrites prior-month revenue allocation when the earlier expected departure is available in audit history. Integer MMK calculations remain in place.
- Payment retries with the same submission key create one ledger entry. Changed details under a reused key are rejected. Check-in retries similarly create one stay and one initial payment.
- Manager-only partial/full payment reversals preserve originals, require reasons, link the original, and identify the operator/time. Excessive refunds and reversals of reversal entries are rejected. Corrections use a reversal followed by a replacement payment; original amount/method/reference cannot be silently edited or deleted.
- Refunds appear as operating cash outflows, while positive receipts remain inflows. Guest balances use signed ledger sums.
- Identity-document viewing and uploading have separate permissions. Existing staff retain their previous permissions during migration; new staff created through administration default to neither permission unless granted. Managers retain access by role. Changes are audited.
- Identity and receipt access is logged with operator, entity, time and IP. Authenticated responses are private/no-store. Generic local-storage serving is disabled. Existing content-based MIME and upload size validation is retained.
- Identity documents and receipts have NO automatic expiration or deletion. Only an explicit, confirmed manager action deletes a file; stay/payment records and deletion audit remain. Deleted identity records cannot be served even if physical cleanup fails. Storage failures are reported for manager follow-up.
- Audit events sanitize password/token/secret/content fields recursively, are append-only through models, include IP, and can be searched by action/entity/operator/date. Database administrators still have database-level access; this is application-level protection, not tamper-proof external log storage.
- Housekeeping now follows dirty -> cleaning -> cleaned -> inspected -> available. Staff start/finish cleaning; managers inspect/release rooms. Responsible employee and timestamps are preserved. Check-in requires available status. Maintenance rejects rooms with future bookings.

Existing safeguards retained:
- Manager-only staff administration, financial statements, expenses and room administration.
- Disabled-account protections, session invalidation on disable/role changes, and last-active-manager protection.
- Unique active room occupancy guard, soft archives, private uploads, historical financial exports, Myanmar/English support and network-only business submissions.

Business interpretation:
A payment refund/reversal changes the payment ledger and increases the outstanding balance; it does not reduce the contracted room charge. The UI explains this before confirmation. A commercial discount or cancellation credit is a separate pricing/accounting decision and is not silently inferred from a refund.
No guest master records were merged by name or phone. A guest page provides a search for stays using the same phone; shared phone numbers must be reviewed by staff.

No dependencies were added or changed.

4. UI/UX REPORT

Main navigation is limited to Dashboard, Rooms, Guests, Reservations, Payments, Reports and Settings. Mobile retains four front-desk tabs plus More. Reports and Settings group less frequent tasks; manager administration remains accessible with role checks. Room setup is collapsed until requested.
Dashboard shows arrivals, departures, overdue stays, cleaning, inspection queue and guest outstanding balances, with check-in/reservation/checkout/search shortcuts. Room cards expose the next valid housekeeping action.
Check-in follows room/dates -> guest -> payment -> review/confirmation. Pricing and remaining balance update automatically; manual prices survive edits/validation. Immediate payment defaults to the full charge; switching to credit makes partial payment explicit. Relevant fields display server validation messages and old inputs are retained. Files must be selected again after a validation redirect, as required by browser security.
Guest pages distinguish unpaid/partially paid/fully paid/refunded states, show the full financial ledger, provide same-phone stay search and manager stay-activity links, and keep private files separate. The Payments page searches guest/phone/room/stay/payment reference. Refund/correction controls are manager-only and collapsed until needed.
Native dialogs are reserved for checkout, financial recording/reversals and deletions. Existing mobile safe-area, touch-size, theme, localization, PWA installation help and offline warnings are retained. Browser-history restoration no longer leaves submission-disabled buttons stuck.

Remaining usability validation: a real receptionist should complete the UAT checklist on the actual front-desk devices. No claim of a user-training study or physical-device certification is made.

5. PRODUCTION READINESS AND RELEASE PROCEDURE

Remaining release gates:
- Controlled UAT and actual Android/iPhone installed-PWA checks.
- Run the new production preflight on cPanel after staging the release/environment and resolve every FAIL.
- Configure and observe scheduled backups, protect backup storage and arrange an off-host copy. A repository scheduler definition alone does not prove cPanel cron runs.
- Verify an actual hosting backup with motel:verify-backup, then perform a recovery drill in a separate staging directory/account.
- Deploy this candidate deliberately; no branches or live files were changed by this implementation task.

Backup automation:
1. Create a private writable directory outside public and storage/app, e.g. /home/sancelno/motel-backups/daily.
2. Set MOTEL_BACKUP_DIRECTORY to that absolute directory in the hosting .env, then refresh cached configuration through the normal deployment process.
3. Configure cPanel cron every minute to run:
   cd /home/sancelno/motel-app && php artisan schedule:run >> storage/logs/scheduler.log 2>&1
   Use the same PHP 8.4 CLI that the existing deployment uses.
4. The scheduler registers a daily 03:00 Asia/Yangon backup with overlap protection. Inspect storage/logs/backup.log and scheduler.log and confirm new backup directories appear.
5. Manual backup:
   php artisan motel:backup /home/sancelno/motel-backups/daily
   This briefly enters maintenance, makes a consistent SQLite copy, copies uploads/environment, records hashes/counts, and verifies a temporary restoration. It restores the prior maintenance state.
6. Verify an existing NEW-format backup:
   php artisan motel:verify-backup /absolute/path/to/timestamp-backup
   The command never replaces the running database. Legacy deployment backups use a different layout and do not have this manifest.
7. Protect backup directories/files; environment backups contain secrets. No automatic deletion of uploads or backups is scheduled. Explicit file deletion affects current storage; historical backup copies require separate manager-controlled handling when fulfilling a deletion or restoration request.

Preflight:
   php artisan motel:production-check
Checks production mode, debug/HTTPS/key/cookies, private-storage exposure/writability, pending migrations, SQLite integrity/foreign keys and backup directory configuration, without printing credentials. Cron execution, real HTTPS responses and off-host backups still require operational checks.

Deployment after controlled UAT:
- Commit only the reviewed application/report changes; preserve unrelated proposal/manual artifacts already present in the workspace.
- Promote the tested commit to demo, test there with synthetic data, then fast-forward prod to that exact commit.
- In cPanel, use the existing bin/deploy-production procedure. It backs up the pre-release database/uploads/environment/hosting settings, preserves the PHP handler, enters maintenance, updates prod, installs locked dependencies, migrates, optimizes and checks record counts.
- Capture the deployed commit and backup location. Run production-check and a new-format backup/verification. Verify HTTPS login, secure cookies, private file access and front-desk workflows without creating fictitious live financial records.
- Do not run migrate:fresh, db:seed or motel:prepare-demo against production.

Rollback / recovery:
- Enter maintenance and preserve a NEW snapshot of the current database/uploads before recovery, including any transactions since deployment. Restoring an older database loses later transactions unless reconciled.
- Restore the exact matching source revision, locked dependencies, .env/encryption key, hosting .htaccess/php.ini, SQLite database and uploads from one consistent backup set. Keep file ownership/permissions correct and remove stale SQLite WAL/SHM only while every writer is stopped.
- New command backups contain database.sqlite, uploads/ (contents of storage/app), environment and manifest.json. Existing deployment backups instead contain revision, hosting.patch, public.htaccess, optional public.php.ini, database.sqlite, environment, record-counts.json and uploads.tar.gz.
- Perform restoration first in an isolated staging copy. For a new backup, verify with motel:verify-backup and inspect all reconciliations. Check DB integrity/foreign keys, expected record counts, referenced files and balances before releasing maintenance.
- Do not simply reset code or drop reversal columns after reversals exist. A complete, reconciled recovery is required. Automatic live restore is intentionally not performed by the verification command.
